# 任务结果判定：同次原生回答、通用标签

开发基线：2026-09-16，文档 PR #18 已合入 `main@2b35390` 后的新开发分支。
本功能尚未部署端侧；用户之前的过夜运行回执属于已有版本，不能算作本功能的实机验收。

## 1. 目标与边界

任务说明中的自然语言就是本次异常判据，不新增业务模板、阈值表、规则引擎、路由模型或独立证据评审 Agent。Skill 继续负责数据语义与检查方法，原 OpenClaw Agent 根据任务说明和实际材料判断。

只给用户三个主要信息：执行是否完成/失败，结果是未见异常/异常/需复核，是否建议推送。
另有未评估、待判定状态，不把缺少评估或无数据说成正常。

```text
任务说明 + 现有 Skill -> 原 OpenClaw 调查和回答（不变）
 -> 同次最终回答附可选短标签
 -> ScopeX 保存原生正文/执行状态，以及独立结果标签
 -> 列表展示与筛选 -> 推送建议（本轮不发送）
```

自动路径不再回灌 Evidence/原图/日志，不追加模型调用，不重跑分析。
这不是独立可信度认证：标签可能继承原模型的误判，`needs_review` 也不能识别所有自信但错误的结论。

## 2. 开关与自然语言判据

`Schedule.assessment_enabled` 默认 true，可在创建表单及已有任务列表切换。旧配置缺该字段时，对**后续触发**按默认 true 处理；不回填历史 Run、不过期补跑、不改计划时间。
每次创建 Run 将开关复制到自己的 metadata，已经排队/执行的 Run 不随之后的开关变化。

普通 `/runs` 默认 false，可创建时显式开启，或结束后点击“手动评估结果”。
关闭自动判定不影响原生正文、任务执行或人工评价。

业务阈值只写任务内容，例如：

> 检查当前宿主机 CPU 和内存，任一项使用率超过80%算异常；明确说明哪项触发，不推断历史持续性。

“任一/同时”“超过/达到”“当前/持续”会影响判断。没有足够说明、必要数据或覆盖，模型应选择需复核；不能从一句话猜出业务意图。这个通用指令不自动解析为第二份数值规则。

## 3. 极小的输出约定，不是报告 schema

启用时在同一次原生最终回答末尾附：

```text
原本就要交付给用户的正文……
<scopex_result>{"status":"abnormal","summary":"CPU使用率超过本任务设定阈值。"}</scopex_result>
```

只接受一个末尾 envelope，两个字段 status/summary，status 为 normal/abnormal/needs_review，summary 最多240字符。没有业务判定目标也不能生成虚假的正常结论。
多个检查项由 Agent 按用户所述的组合条件判断；没有确定异常而有必要项未判定则需复核，只有目标范围检查足够且未触发才未见异常。

解析器仅校验小标签的格式，不检查正文语义，不把关键词“异常”当判定，也不识别或计算 CPU 阈值。重复/缺失/非法标签 -> 需复核，不自动重试、不调用格式修复模型、不让本来已完成的任务失败。

`report_text`/`final.txt` 保持原生文本（沿用原有脱敏/长度限制）；合法 footer 原样记录在 `report_meta.assessment_footer`，UI仅隐藏这个精确末尾片段。原始审计保留可复盘内容，不静默改写正文。

原生预算中断/error/length/进程失败继续走原有 FAILED + partial/unavailable，标签不能将其升级成功。系统 Locator no_data 记录需复核，不据此推送设备故障。

## 4. 保存、列表与推送建议

`assessment.json` 保存当前判定；`task.json.metadata.assessment` 为列表摘要；手动操作另追加 `assessment-history.jsonl`。保留来源 native/native_reuse/manual_text/system、原正文/请求哈希、更新时间和手动调用尝试次数。

任务列表 GET /tasks 新增可选 state、assessment_status、push_decision；**先过滤再分页**，可与 day/schedule_id 组合。读取任务元数据，不读取正文、Evidence或调用模型；没有新建磁盘索引，仍沿用现有文件枚举。

原有运行状态独立。推送建议：异常 -> suggested；未见异常或需复核 -> none；未评估/待判定 -> undecided。
`delivery_status=not_connected` 始终明确，本轮没有平台端点、发送重试、设备动作或网络投递。建议不是实际投递，也不是未来发送资格；历史重评不会自动发通知。后续连接平台仍需显式开关、时效和防重复等通用控制。

## 5. 普通任务的手动操作

GET `/tasks/{id}/assessment` 只读摘要。
POST `/tasks/{id}/assessment`：`{"allow_model":true,"retry":false}`。
只允许终态任务。已经有结果时默认返回原评估，重复点击不重复调用；再次尝试需用户显式 retry。失败任务、无数据和无正文直接需复核，不调用模型。合法已有 footer 直接复用。

无可用 footer 的完成任务，只有显式 allow_model=true 才调用本机模型一次。UI点击前说明其成本/范围。输入仅原任务说明、原请求/计划时刻、有效 STEER/RESUME 控制记录和已保存正文，不传 Evidence、路径文件内容或图片，不恢复原 Session、不调用工具。不将历史辅助压缩响应当答案。

复用既有 loopback 模型客户端。输入含系统说明的 UTF-8 总字节最多12000，输出256 tokens，通信超时60秒，响应流上限64KiB并检查处理期限；超限不静默截断输入，不自动重试。这不是固定总耗时或吞吐保证。

仅在没有活动/排队任务时开始，最多一个手动文本评估在进行；繁忙返回409且不改变结果。之后新来的普通任务不被评估阻止，因此已经发出的短请求仍可能短暂共享模型容量，不能宣传完全不影响吞吐。

`source=manual_text`、model_calls 单独记录；原任务的 postprocess_model_calls=0 不被改成隐藏追加报告调用。归类只判断原正文表达，不声称独立核验其事实。正文不足/控制上下文不可用/调用失败等 -> 需复核。不会覆盖 result.json、原任务完成时刻或执行状态。

切换/重启不重跑评估，遗留 pending 置需复核；评估期间禁止删除同任务，避免写回已删除目录。终态删除清理评估资产而不删除业务源；review ZIP包含评估文件。

## 6. 验证范围

新增合成回归覆盖：

- 标签成功/缺失/重复/非法字段/引用示例/超限与执行状态分离，原生正文和零额外模型调用；
- 定时开关默认/关闭/保存/下一次触发，原任务说明不变；
- 手动显式授权、零调用复用、忙碌拒绝、重复点击、删除互斥、重启不重评；
- 列表筛选在分页之前，不读报告或证据；HTTP布尔类型校验；
- 仅短文本与原控制上下文进入一次请求，预算、错误/截断/无工具、脱敏。

这些测试替换原生模型执行或短文本响应，不证明真实模型能稳定解释80%边界、任一/同时，或正确识别相机/编码器异常。

实机应先对比同任务开启/关闭后的正文质量、调用数、耗时和截断；再人工核对阈值边界、缺项/无数据、正常后退/归零、相机仅样本异常等结果。没有真实结果前不填写准确率、需复核率或性能改善百分比。

现行原生结果架构、现场 Compose/模型/阈值、历史状态均未因此重新设计或部署。
