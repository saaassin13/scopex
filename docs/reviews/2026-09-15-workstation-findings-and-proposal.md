## 3. 决定方案的关键证据

### 3.1 图片任务已经答对主要现象，却在交付前失败

`task-fc80d6ff2f20` 的 `wire-07-response.bin` 正常 finish=stop，正文明确指出四张图有雾状遮罩、发软、疑似脏污。之后 wire08–11 全部是无工具的 context summarization 调用，并非继续视觉检查。

最后一次压缩被600秒任务 deadline中止；stderr记录 `context-engine compaction failed`，compaction durationMs=384352。CLI stdout为空。ScopeX 随后走 Evidence 报告，因 #16 输入膨胀在请求模型前拒绝，显示 text_report_unavailable。

所以这是两段独立故障：

1. 已生成的答案被后置压缩和总预算取消挡住；
2. fallback 报告输入容量失败。

#17 修第二段重复元数据，不处理第一段后置压缩。

原答案也不是完美真值：从四张图和相近指标推断“全时段持续”仍过强；把上方栏杆附近斑点认定镜头污染也需区分场景自身污迹。但“识别不到明显图像劣化”不是这次任务的主要失败。

### 3.2 原生配置已经能解决这类后置维护，不需自建调度

现场安装包文档：

- `docs/concepts/compaction.md:43`：`agent --local` 在完成 turn 后执行 usage-based maintenance。
- 同文件`:45`：正常压缩失败可返回已完成回复，但 cancellation/restart/replaced session 会阻止返回。
- 同文件`:47`：`agents.defaults.compaction.enabled=false` 关闭 proactive threshold 和 direct-command post-turn maintenance；原生 preflight、overflow recovery 和手动 compact仍可用。
- `docs/reference/session-management-compaction.md:262`、`:289` 对上述行为有对应说明。

ScopeX已有 `--disable-compaction`，会映射此原生设置。建议对当前独立一次性任务首先验证使用这一设置；不是修改 OpenClaw 包或编写自己的 compactor，也不是取消全部上下文溢出恢复。持续会话若未来恢复，需要重新评估产品配置，不能扩大为全场景永久关闭的结论。

### 3.3 报告额外调用确实引入新的错误

13点编码器：

- 工具完整事件最大回退是 **1863 count，13:28:43.258–13:28:43.911**；原始相邻日志已核对计数从2448365下降到2446502。
- 初始聚合 Evidence 的 max_reverse_pulses=1863，但 top10全部是flat；当前排序问题在真实任务中复现。
- Agent又读取events_out，输出15,944字符；这些细节再次被投影限长。
- 原生答案声称最大1451；额外报告又声称最大895。两者均与完整事件以及汇总最大值不一致。不能宣传直接答案天然准确，必须同时修业务输出与评测。
- 原生答案将84段flat归为可能正常停机、不计异常；报告却把flat放进“主要异常”第一类。

12点编码器额外报告用了1730 completion tokens、232.5秒，重复字段解释、候选免责声明和泛化排查建议，还加入无关的“无图像证据”。可读性与任务价值并未随篇幅增加。

旁证：同批CPU/内存报告在一份快照上写“无内存泄漏”和“当前没有排队等待进程”，并将1min>5min>15min解释成负载下降。说明生成成功不代表语义正确，问题不是只会出现在编码器。

### 3.4 工况解释不足，不应把现有候选直接认定为硬件问题

12点最大回退附近原始应用记录呈现连续变化：12:47:39正速减小，12:47:40转负，12:47:41–42负速幅度增大，12:47:43–45回到近零。更适合描述为一段连续反向变化过程，而不是仅凭总回退量与单步中位数对比认定毛刺。

不能因此认定它正常：是否为允许的机械回弹、实际反转或其他行为仍需要同类正常过程和现场口径。报告出的 TurnTableSpeed 也可能由同一计数派生，不能当独立传感器真值。

## 4. 推荐方案：按最小改动形成统一主链

### A. 正常完成走原生答案；异常结束有明确草稿/失败

推荐主链：用户目标 → OpenClaw + 业务Skill/工具 → OpenClaw最终答案 → ScopeX展示、来源附件及审计。

- 正常完成用已经存在的 cli_outcome.answer/payloads，不再强制业务任务进入第二次 TextReportComposer；这与已有普通 conversation 路径复用能力一致。
- ScopeX保留权限、Sandbox、任务隔离、时间锚点、来源身份、审计和状态。不恢复 Claims/枚举/JSON 必经链。
- 原始工具结果与来源完整保存在审计，展示摘要由业务工具/Skill有界提供；不按业务字段白名单隐式丢限制、单位和语义。
- 未完成的回答与执行状态分开；不能从任意一条 wire stop 直接判断整个 Agent成功（压缩等辅助调用也会 stop）。优先消费 OpenClaw原生完成信号；本次不新建SSE协议解释器或另一份会话状态机。
- 现有文本回放保留为人工复盘能力。中断fallback是否保留一次报告取决于有无可用原生答案、实际必要性；不默认再次诊断，不把草稿标成成功。
- 先验证现有 `--disable-compaction` 对独立任务的作用及原生溢出恢复，不通过调大600秒预算掩盖交付问题。

验收：8点图片固定任务能够交付其正常完成答案；大输入仍受控；正常答案不再付出第二次报告调用。保留异常路径测试，不承诺新时长等于历史wire时刻。

### B. 编码器工具提供足够事实，Skill负责区别正常工况

- 按连续时间段和实际dt处理，不跨无效/复位边界连接。
- 区分停转、起步/减速、稳定运动和反向变化的观测形态；计算仍用现有标准库与脚本能力。
- 以count/s、持续时间、前后正常区间、反向过程和恢复过程判断偏离；不把多个样本总回退量直接同一个正常单步增量比较。
- 相邻启停中的回弹/震荡应合并为同一过程供判断，不机械累计几十个独立报警。
- 正常停转与异常候选分开输出；最重要事件详情必须覆盖全局极值，不能被flat排序挤掉。提供有界事件查询接口/脚本选项，复用现有events_out，避免Agent临时写Python并打印全部事件。
- 对关键候选主动读局部上下文以判别是否异常；不等用户另问“为什么”才补。缺运动指令/正常样本时明确未定，不要求全项目源码调查。
- 正常启停/回弹样本与已确认异常样本分别验证误报、漏报、定位和解释。阈值不在本次无标签数据上直接定死。

这是一项业务分析能力，放在 encoder Skill/工具中；不是把异常检测规则塞进 ScopeX Runtime。

### C. 图片先发现退化，再按需要定位时间段

- 首轮直接看按时间覆盖的少量原图，避免默认 --help、指标计算及反复脚本探索。
- 指标仅在有明确筛查价值时计算；沿用已有工具。指标相近不能证明全时段正常，也不能证明全时段污染。
- 对疑似区间保留邻近帧复核额度，用于区分偶发、多个时点反复出现与有观测支持的连续区间。输出观测边界和未知间隔，不虚构精确起止。
- 视觉判断先回答质量是否下降、影响区域/程度，再区分模糊、雾状遮罩、污物或水滴等可见特征；物理原因最后给可能性。
- 明确设置并验证ScopeX与vLLM的图片容量一致，但不要求每次用满12张。8张/12张全尺寸容量仍需真实请求验收。
- 正常结果不二次看图。原图来源/哈希继续保留，不把去掉重复视觉调用等同去掉溯源。
- 暂不新增分类模型、训练管线或复杂CV依赖；先用已确认可识别的现场样本检验现有模型与改进流程。

### D. 提示词整理依据真实加载链

已从wire确认：OpenClaw系统提示词含六个Skill的描述/路径，而不是六份正文；业务任务再按需read。不能声称“所有Skill全文都被默认塞入”。系统文本约9069字符，Runtime用户前缀约4190字符；图片Skill正文6836字符、locator2149字符。

- 不编辑第三方OpenClaw提示词或安装包。用原生配置处理原生能力。
- Runtime只保留动态能力、权限、目录/时间和预算。避免加入跨业务故障示例或视觉操作流程。
- Skill保留领域判断、工具用法和停止条件，合并重复禁令；工具用法足够明确以免额外 --help。
- 输出要求写在调查的同一上下文中：直接回答、关键证据、覆盖限制、必要下一步。不要求重复大表、脚本字段名及与任务无关的“没有图片”说明。
- 工具JSON保留计算能力，不要求自然语言报告通过Claims结构门槛。语义正确性靠固定样本评测与人工标注验证。

### E. 并发性能最后独立验证

先建立单任务正确性和耗时基线。随后在另行获准的维护窗口验证vLLM 2序列配置与ScopeX 2名额，保持模型不变，比较同一批任务总时长、结果覆盖、资源影响。当前只提出方案，未调整容器。

## 5. 实施顺序与讨论点

建议按 A → B → C → E 推进，D随受影响环节整理，不单独发动全仓库提示词重写。

先讨论的架构决定：是否采用“正常业务任务直接交付OpenClaw答案，独立报告退出默认主链”。本次证据支持该方向，但不是说原生答案没有错误；B/C的业务质量改进必须同时作为后续验收目标。

实现前用少量现有样本共同确认正常回弹与应关注异常的口径。没有标签的连续回退不自动当正常，也不当硬件故障。先完成两个Skill，不扩展其他业务。
