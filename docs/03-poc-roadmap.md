# POC 路线与阶段门

不预设任何 Agent/模型胜出。继承 OpenCode/OpenClaw 旧验证；先取证，后控制变量。基础探针不是自研 Agent 产品。

| 阶段 | 关键问题 | 主要输入/操作 | 交付与阶段门 |
|---|---|---|---|
| 基线整理（并入 POC01 前半） | 要改善什么、怎么判 | 保留原日志、原要求、正确答案、现有配置；未知信息明确留空 | 需求、版本记录、真值与旧失败证据，不伪造原因 |
| **POC01** | 理解能力、工具协议和短链路分别是否可用 | 同内容 direct/tool 对照，空结果、列目录+两次读取、实际双图输入、原失败日志 | [逐步执行手册](poc/01-spark-runbook.md)、运行记录与失败分类；满足阶段门才扩大范围 |
| POC02 | 现成 Agent 能否自主完成并收尾 | 同一模型设置和任务比较少量运行时；先最多两个候选 | 任务正确性、时间、无效动作、真实工具/图片传递；每次复测写改变量 |
| POC03 | 知识和 Skill 是否改善业务任务 | 日志、图像与服务三个闭环；变时间、目录、缺字段、新格式 | 能力包与有/无知识对照；不把答案或整条流程写入 Skill |
| POC04 | 对话干预和权限是否成立 | 生成中断、命令中断、改条件、重连继续、拒绝授权、数据内伪指令 | 实际接管和副作用边界通过；用隔离环境或维护窗口 |
| POC05 | 可重复、离线和共存是否成立 | 固定案例重复、留出集、断网重启、混合连续负载 | 试用部署包、实测指标、已知限制、是否交付结论 |

## POC01 不测什么

不安装新模型、不选择新运行时、不执行通用 Shell、不修改生产文件、不测复杂 Skill/RAG、不构建 UI，也不把 Ctrl-C 的探针行为当作最终会话可干预验收。自动读取脚本是协议探针，不是目标产品。

## POC01 的阶段门

1. 单次冒烟先全部正确，且基础协议清楚；失败默认立即停止，先看错误记录。
2. 正式基础测试，各文本用例分别5次；要求 direct-basic、tool-basic、direct-empty、tool-empty、chain 各5/5准确。五次很少，此门只控制下一阶段投入，不声称95%可靠性。
3. 上述简单文本任务希望至少4/5在120秒内完成，才能作为速度有希望的候选；这比最终90%目标宽，仅为早期筛选。超出则标记性能问题，先定位而不盲目扩大。
4. vision 与 vision-swap 各5/5，才标记基础双图链路成立。未支持或未运行必须记为视觉未通过，不能以文本通过宣称满足完整需求。
5. 原来失败的真实日志必须独立核对后重复；没有拿到原始材料只能是“合成探针临时通过”，不能宣布原问题已解决。
6. 以上仍不代表完整 Agent、通用聊天质量、复杂业务诊断或离线产品交付通过。真实日志的最初原要求与本探针 JSON 输出约定不同，必须记录差别。

## 变更顺序

保持已有服务做 baseline → 核对协议/推理实际配置 → 只改一个已知因素并重复 → 必要时比较第二个模型/后端配置 → 最后进入运行时比较。

配置改变需新标签和新配置副本；不得覆盖旧样本/报告。输出预算触顶时可以单独扩大预算做对照，但必须保留原失败，不能当成同条件复测。出现 OOM、业务延迟、服务失联立即停止，不持续跑批或自动重启。
