# 通用 Agent、结果链与首批业务 Skill 审查

日期：2026-09-15。代码基线：`d1b5a081a58877aa4e0239dc9e1ace27fb11accd`。

后续已读取现场任务、wire与8张获准原图，见 [Workstation 实际复盘与待讨论方案](2026-09-15-workstation-findings-and-proposal.md)。本文件的“未验证”描述是初轮状态，当前以该补充报告为准。

## 目标与范围

用户明确保留 OpenClaw，审查 ScopeX 是否过度封装、重复实现。优先解决结果处理反复修复、编码器异常识别、图片质量诊断；两项业务有效后再接其他 Skill。本报告是只读分析及合成反例验证，不包含功能修改或现场部署。

编码器的目标是识别不符合正常运行规律的事件，必须考虑启动、停止和机械回弹。图片的目标是识别对焦、模糊、起雾、脏污、水珠等质量问题，并考虑持续性。

已读：需求、阶段交接、最新输出/并发方案、OpenClaw 边界、历史结果方案与真实失败复盘；当前执行配置、结果链、Evidence 投影、两个 Skill 及脚本、相关测试和提交历史。对照了本机 `diagnose-encoder-logs` 的 Skill 与分析脚本。未调用该 Skill 执行现场日志诊断。

未验证：Spark 当前运行版本、OpenClaw 原生实际生成的完整系统提示词、真实模型请求、原图视觉质量、业务误报漏报率和现场性能。本地没有可直接调用的 OpenClaw CLI；不据此判断现场缺失。

## 结论

1. 目前最明确的架构问题在结果交接：ScopeX 从调查材料中筛选、删字段、截断，再让一个没有业务 Skill 上下文的模型重新解释。它已超出单纯的身份记录和展示。
2. 编码器目前实现的是阈值候选提取，尚不满足正常启停/回弹与异常的业务区分。提示词表达了部分正确原则，但脚本、字段名和示例未贯彻。
3. 图片 Skill 的视觉维度较完整，但当前少量抽样不能定位连续问题的起止；报告阶段再次看图，增加了独立解释和推理开销。实际瓶颈与模型能力仍需现场样本判定。
4. 不能因此认定全部封装都应删除。任务生命周期、隔离、权限配置、来源身份、审计有明确产品责任。已读配置把工具执行、compaction 和 loop detection 交给 OpenClaw，未见另一个逐工具调查调度器。

## 一、结果链为何反复修复

历史动机合理：POC05 的自由文本将退出状态升级为 OOM、时间关联升级为因果；POC06 因此引入 Claims 和校验。随后增加去重、枚举规范化、引用数量规则、结果编辑器。真实聚合统计又因共用 E1 被拒绝。PR #15 修结构化恢复，#16 删除强制 Claims 主链，#17 修新文本链重复元数据导致输入膨胀。

这是从“控制语义错误”转向“满足结构协议”、再撤销部分协议的演变。历史设计有其动机；但结构通过不能等同业务判断正确，不能恢复 Claims 强制链作为默认建议。

### R1：通用 Evidence 层按业务字段白名单删内容（高优先级，已复现）

位置：`scopex/evidence/projector.py:214`，`_compact_business_facts`。

- 只保留固定字段；编码器脚本输出的 `semantics` 被删除。
- 新 Skill 顶层的 `units`、`limitations`、`result` 等也不会自动保留。支持新字段需要遵从现有特殊结构或修改核心层。
- `top_candidates` 被再次缩到 10 条。超容量时依次删除 logs、per_file_matching_samples、top_candidates、quality；仍超长则直接切字符串。
- 默认 12,000 字符的截断可能产生不完整 JSON。该结构化分支未为每项删除提供明确的语义损失记录。

合成验证直接调用当前方法：semantics 被删除；新 Skill 的 units/limitations/result 被删除；13,000 字符 facts 经裁剪后 `json.loads` 失败。

影响：报告输入损失发生在 TextReportComposer 之前。报告“不改变范围与限制”的提示词无法恢复未收到的限制。#17 的无损分组只作用于已投影的 Evidence，不能修复上游丢失。

建议：确立一个小的通用工具结果契约，领域数据由 Skill 自己有界组织；核心不按业务内容删字段。限制、覆盖、单位、候选性质必须与数据一起保留；超容量显式说明，不能切成残缺事实。无需建立逐业务翻译器。

### R2：报告编辑器实际承担第二次解释，但没有领域上下文（高优先级，已核对代码）

位置：`scopex/agent/runtime.py:286`、`scopex/runtime/investigation.py:345`、`scopex/finalizer/text_report.py:14`。

调查终答被要求简短交接；新报告输入只包含原目标、控制记录、结束原因和 Evidence，未传入所用 Skill、调查结论与排除理由。Skill/源码被正确排除出业务 Evidence，但没有作为独立领域说明传递。报告模型还被要求重新查看原图。

因此它不是纯排版：它需要重新解释候选含义、图像和业务语义。通用报告 Prompt 中的“候选事件数不是脉冲幅度”“缺失不等于零”等已经承担了部分领域解释职责，新增业务容易继续往这里加补丁。

建议先比较两条路线，而不立即替换主链：

- 正常完成时让 OpenClaw 在已有上下文中直接交付答案，ScopeX 保存答案、来源和执行状态；另行检验如何展示引用、范围与中断情况。
- 若保留报告调用，传递最小交接材料：结论、对应依据、已排除解释、限制及相关领域语义。它们不是新证据，也不自动可信，但不能完全丢弃后要求编辑器自行恢复。

中断后的依据报告与正常完成后的最终答案可以有不同需要。不建议每个任务都强制经过同样多次独立解释，也不建议立即取消全部输出边界。

### R3：当前容量保护分散，失败条件仍存在（风险）

TextReportComposer 保留 48,000 文本字符门槛；图片另有数量、单图字节限制，不能等同模型 token 容量。ModelProxy 调查请求体上限为 4 MiB；报告通过独立 client 附原图。不同路径的预算不是一个概念。

需要按实际 wire 请求测量文本 token、图片处理后 token、请求字节和输出长度，不能简单增加一个图片数量配置就认为容量解决。此处未证明某个真实图片任务触发了 4 MiB 限制。

## 二、编码器 Skill

### E1：正跳变比较未按真实 dt 归一化（高优先级，已复现）

位置：`skills/encoder-health/scripts/encoder_health.py:166`、`:280`。

局部基线取前后 20 个增量的正值，不比较 count/s。dt 仅用于排除超过 gap 门槛的记录。

合成反例：全程 1,000 count/s，通常 20ms 增加 20，某一次 80ms 增加 80，随后恢复 20ms。当前返回 `positive_spike_candidate`，阈值为 60，且 sampling_gap_count=0。位置增长速率完全一致，算法却标出脉冲跳变候选。

建议：按实际时间比较变化率，并对启停过渡与稳定运行分别判断。采样节奏改变和运动异常分开描述；不要求距离标定即可使用 count/s。

### E2：没有正常回弹判别，候选被计入 anomaly_event_count（高优先级）

位置：同脚本 `:190`、`:478`；`skills/encoder-health/SKILL.md:78`。

负增量按幅度及后续三个样本是否恢复分类。检测不使用已读取的 speed 字段识别启停；没有停后回弹包络或同类周期对照。

合成“运行→减速→停止→回退 8 count→静止”得到 reverse_step_candidate。这个例子只证明算法不区分回弹，不能证明现场 8 count 一定属于正常范围。

此外所有 reverse 候选进入 anomaly_event_count；Skill 一方面提醒不是硬件故障，另一方面建议直接报告“发现 3 个显著异常事件”。“不是硬件故障”并不等于“已区分正常运动”。

Skill 还把补充上下文放在用户询问原因/影响时才使用，但有些局部上下文在判断是否异常时就需要。

建议：保留候选提取作为工具能力，进一步区分正常可解释、偏离正常规律、证据不足。正常包络需从现场代表数据验证，不能凭本次讨论发明阈值。候选计数、已判异常数量、未知数量分开。

### E3：正常停转会挤掉跳变详情（高优先级，已复现）

位置：同脚本 `:384`、`:493`。

severity 直接混排毫秒和脉冲数：flat 的 2,000ms 比 spike 的 500 count 大。默认取前 12 项，再由 Evidence 层缩到 10 项。

合成排序：12 个两秒正常停转加一个 500 count 跳变，top12 全部是 flat。模型可看到异常总数，却看不到对应事件细节；events_out 虽保存完整结果，默认“分析一次后简报”的路径不保证补读。

建议：正常工况与待判异常分开呈现；异常按偏离程度、持续时间及可信度选取，不能跨量纲直接排序。

### E4：Codex Skill 的方法没有完整落到当前交付链

本机参考 Skill 明确要求结合 dt、启停、恢复、近停回弹、正常对照和周期证据；它本质上依赖 Agent 解释，不是单靠分析脚本自动作出业务判断。

当前 ScopeX 保留了部分文字原则，却将候选检测及“简短调查→独立报告”串起来。参考同一个 Skill 不等于保留同样的分析效果。现有相关测试覆盖毛刺、连续回退、无效记录断点，但这些测试不证明正常启停/回弹误报率合格。

## 三、图片质量 Skill

### I1：能检查样本，不等于能识别连续区间（需求缺口）

位置：`skills/image-quality-diagnosis/SKILL.md:38`；`skills/data-locator/scripts/data_locator.py:113`。

当前流程少量代表图→视觉判断→描述 isolated/persistent。没有可复用的时间邻域复核、起止定位或未观察区间表示方法。Locator 的 evenly_spaced 实际按排序后的文件序号取样；当图片时间密度不均时，不等于按时间均匀覆盖。

多个时点都有雾化可支持“所见样本反复存在”；不能据此证明中间一直存在、何时开始、何时消失。若早期少量图片用完累计额度，也没有余量验证疑似区间边界。

建议：先明确需要粗筛发现还是时间区间定位。以时间分段筛查，再针对疑似变化补看邻近原图，预留复核预算；输出观测时段和未知间隔。确定性取样/邻域取图适合放业务工具，不需要新增核心工作流引擎。

### I2：二次看图增加调用与判断分叉（已核对路径，性能收益未测）

调查通过 view_image 看图；报告重新加载并校验原图，独立视觉解释。原图校验有溯源价值，但独立第二次推理不自动等于更准确，也可能出现调查与报告判断不同。

当前累积式上下文中前面图片会随后续请求继续出现；实际缓存是否复用、图像编码是否重复、各阶段占时，必须看现场请求与服务指标。

建议用同一批图对照：调查直接回答与现有重读报告。分别评价视觉正确性、原图覆盖、输出稳定性、模型调用及耗时。不能仅凭架构认定视觉模型差，也不能承诺省掉报告后固定加速比例。

### I3：指标与业务用途没有形成验证闭环

现有 metrics 工具计算全图锐度、梯度、亮度和对比度。Skill 正确强调指标不能判定无雾、无污；但指标也没有自动保证覆盖低质小区域或持续污染。

需要样本区分正常场景纹理变化、运动模糊、失焦、雾化、污点、水珠及混合情况。评价重点还应包括关键业务区域是否可用；不在未确认前把某个固定 ROI 或阈值写死。部分原因视觉上难以唯一确定，应允许“可见模糊，原因未定”。

## 四、提示词职责地图

| 层 | 当前内容 | 建议职责 |
|---|---|---|
| OpenClaw 原生提示词/工具定义 | 本地仅核对接入配置，实际内容未捕获 | 保留执行、工具调用及上下文管理 |
| Runtime capability | 范围、目录、权限、scratch、图片步骤、终答交接 | 保留客观能力、动态预算和时间锚点；业务取样方法归 Skill |
| Data catalog / data-locator | 位置和访问约束 | 单一目录语义来源，工具返回覆盖与截断状态 |
| 业务 Skill | 分析方法、停止原则、业务语义、报告示例 | 区分正常与异常的方法；不把候选示例写成已确认结果 |
| 工具输出 | 统计、候选、semantics | 自描述、范围完整、大小有界；保留关键限制 |
| Evidence 投影 | 删字段、限候选、截内容、记录来源 | 身份与来源、显式容量状态；不进行隐式业务裁剪 |
| TextReportComposer | 通用表达及零散领域约束、重新看图 | 若保留，负责可读表达；领域语义来自当前任务，不堆进全局 Prompt |
| 历史 Claims/JSON Composer | 旧路径和专项兼容 | 不当作当前主链，不为修复新业务继续加协议 |

并非重复一句原则就需要删除。是否影响效果要看实际激活内容、冲突及 token。尤其不能把所有 Skill 全文复制到报告里作为补救。

## 五、建议实施与验证顺序（尚未执行）

1. 先明确结果交接契约，修复丢语义、混量纲排序等可确定问题；保持业务方法在 Skill/工具层。决定是否保留独立报告应做小规模对照，不立即重写全部输出链。
2. 编码器优先：准备正常启停/回弹、稳定运行、已确认异常的标注窗口；比较当前与候选方法的误报/漏报及事件定位。正常反例优先于新增更多异常规则。
3. 图片其次：准备正常、各类低质、持续与间歇变化的原图序列，固定时间范围，比较选样覆盖、诊断及调用耗时；明确是否要求起止定位。
4. 用上述固定样本评估结果链两条路线，验证语义保留与总耗时。保留失败样例为回归输入，而不是为每种失败新增硬编码提示词。
5. 两项业务达标后再接新 Skill。之后再做整批并发性能验收，避免把少分析、少看图当加速。

所需外部证据：现有失败任务复盘包的位置、正常启停/回弹与异常日志窗口、包含质量变化的图片序列，以及用户认可的异常/正常或可用/不可用判断。先复用已有材料，不要求先重跑生产。
